## 본문

### '같은 코드'를 먼저 구체적으로 말하기

어제는 잘 읽히던 로그가 오늘은 다르게 계산된다고 하자. “같은 프로그램을 썼다”는 말에는 프로그램의 어느 상태인지 빠져 있다. Git 커밋은 기록한 파일들의 특정 상태를 식별하는 데 도움이 된다. 하지만 커밋 뒤 작업 트리에서 소스를 고쳤거나 추적하지 않는 설정 파일을 바꾸었다면 같은 커밋 ID를 표시해도 실제 실행 내용은 달라질 수 있다.

작업 트리는 현재 파일을 편집하는 영역이고, 스테이징 영역은 다음 커밋에 넣을 상태를 준비하는 영역이다. 모든 수정이 자동으로 커밋되거나 서버에 올라가는 것은 아니다. [Pro Git의 변경 기록 설명](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository)은 추적된 파일·미추적 파일과 상태를 구분한다. 읽기 확인에서는 `git status --short`로 상태를 보고, `git diff`와 `git diff --cached`로 스테이징 전후의 차이를 구분할 수 있다. 명령의 이름을 외우는 것보다 어느 두 상태를 비교하는지 설명하는 것이 중요하다.

미추적 파일의 내용이나 저장소 밖 데이터는 커밋 ID만으로 복원되지 않는다. ignore 규칙으로 제외한 대형 로그·지역 설정도 별도 관리해야 한다. 그렇다고 인증정보를 모두 저장소에 넣어 재현성을 높이는 방식은 적절하지 않다. 재현에 필요한 설정 항목의 이름·사용한 값의 비민감 부분·외부 의존성 식별자를 구분해 기록한다. 이 단위는 실제 저장소의 reset·삭제·이력 재작성 같은 변경을 요구하지 않는다.

### 소스와 패키지, 데이터는 다른 층이다

Python 코드가 같아도 실행 인터프리터나 패키지 버전, C++ 컴파일러 옵션과 연결 라이브러리가 다르면 결과나 실행 가능성이 달라질 수 있다. 의존성 목록과 잠금(lock) 기록은 사용한 버전·해결된 의존성을 재구성하는 데 도움이 된다. 그러나 잠금 파일 하나가 운영체제·장치 드라이버·모든 외부 데이터를 자동으로 고정하지는 않는다. 무엇을 고정하는 파일인지부터 읽어야 한다.

데이터도 파일명만으로 같다고 할 수 없다. `run.csv`라는 이름을 유지하며 내용을 바꿀 수 있기 때문이다. 내용 해시와 자료 수집 조건·전처리 방식을 기록하면 다른 입력을 같은 실험으로 오인할 위험을 줄일 수 있다. 해시가 같다는 것은 기록한 바이트의 동일성을 확인하는 근거이지 센서가 정확했다는 증명은 아니다. 단위·좌표·기간·누락 등 데이터 의미는 별도 계약이다.

venv는 프로젝트의 Python 패키지 환경을 분리하지만 다른 위치로 폴더만 옮기면 그대로 재현된다고 보장하지 않는다. [Python 공식 venv 문서](https://docs.python.org/3.12/library/venv.html)는 환경을 옮겨 다니는 코드 보관소보다 재생성할 수 있는 환경으로 다루도록 안내한다. 사용한 Python·의존성 명세·설치 경로 조건을 기록하고 새 환경에서 다시 구성·확인하는 접근이 필요하다.

### AI 모델과 native 산출물의 재현 명세

AI 입력에는 모델 가중치뿐 아니라 축·채널 순서, 단위, 정규화 통계와 행동 표현이 연결된다. 같은 가중치 파일을 써도 전처리 통계가 바뀌면 모델에 들어가는 값이 달라질 수 있다. 가중치·통계·교정 설정 각각의 식별자와 이들을 묶는 설정 revision을 기록한다. 한 파일의 해시를 전체 실행 계약의 해시처럼 해석하지 않는다. 교정 파일이 같다는 사실도 현재 장치 위치와 교정 조건이 여전히 맞다는 증거는 아니다.

합성 예로 입력 위치가 250 mm이면 먼저 0.250 m로 바꾼다. 정규화 계약이 ‘입력에서 평균을 빼고 표준편차로 나눈다’이고 A의 평균이 0.100 m, 표준편차가 0.050 m라면 결과는 (0.250−0.100)/0.050=3이다. B의 통계가 평균 0.200 m, 표준편차 0.100 m라면 결과는 0.5다. 두 값은 무차원이며 같은 가중치라도 입력은 같지 않다. 이 예는 학습이나 추론을 실행한 결과가 아니라 전처리 계약의 계산이다.

native 확장은 소스·패키지 버전과 함께 실제 빌드 산출물·CPU 대상·인터프리터 ABI·컴파일/링크 옵션을 기록한다. [pip의 반복 설치 안내](https://pip.pypa.io/en/stable/topics/repeatable-installs/)는 버전 고정과 다운로드 파일 해시를 구분하고, 컴파일한 wheel 묶음이 운영체제·아키텍처에 종속될 수 있음을 설명한다. 같은 요구 목록을 다른 플랫폼에서 해결했다고 같은 바이너리가 만들어졌다는 뜻은 아니다. 빌드 도구와 실제 로드 경로를 M01.03~04의 기록과 연결한다.

### 컨테이너 태그와 고정된 내용 구분하기

컨테이너 이미지는 사용자 공간의 파일과 실행 구성을 묶어 환경 차이를 줄인다. 이미지 태그는 이름표이며 같은 태그가 나중에 다른 내용을 가리킬 수 있다. digest는 특정 이미지 내용의 식별에 사용된다. [Docker의 공식 빌드 권고](https://docs.docker.com/build/building/best-practices/)는 base image 버전과 digest를 다루면서 고정·갱신 관리의 필요성을 설명한다.

특정 이미지 digest를 적어도 호스트의 커널·장치·GPU 드라이버·바깥에서 연결한 데이터와 설정이 모두 이미지에 들어 있는 것은 아니다. 여러 플랫폼을 지원하는 이미지라면 실제 사용한 플랫폼도 확인해야 한다. 컨테이너 실행 때 외부 디렉터리를 연결하면 이미지 밖의 파일이 결과를 바꿀 수 있다. 따라서 “Docker를 썼으므로 어디서나 똑같다”보다 어떤 이미지·플랫폼·외부 입력·실행 옵션을 사용했는지 기록한다.

내용을 고정하는 것과 최신 수정 사항을 검토하는 일도 별개다. 영원히 오래된 이미지에 머무르는 것이 재현의 목적은 아니다. 변경 전후 식별자와 결과를 비교해 업데이트의 영향을 추적할 수 있어야 한다. 여기서는 실제 이미지를 내려받거나 드라이버를 바꾸지 않고 합성 기록의 불일치만 분석한다.

### 결과의 재현 범위도 미리 정의한다

어떤 실험에서는 출력 텍스트가 정확히 일치해야 하고, 어떤 수치 실험에서는 정한 오차 범위와 성공 조건을 비교해야 한다. 난수 시드 하나가 모든 병렬 계산·외부 시간·장치 차이까지 없애는 것은 아니다. 무엇을 동일하게 유지하고 어떤 차이를 허용할지 정하지 않으면 결과가 달랐을 때 결함인지 허용된 차이인지 판단할 수 없다. [PyTorch 재현성 공식 안내](https://docs.pytorch.org/docs/2.15/notes/randomness.html)도 release·플랫폼과 CPU/GPU 간 동일 결과를 시드만으로 보장하지 않는다. 실제 사용하는 연산·장치·라이브러리 버전과 결정성 설정의 적용 범위를 확인한다.

비교 기준은 결과를 보기 전에 정한다. 예를 들어 이 단위의 로그 변환을 같은 입력에서 확인할 때 위치 오차의 절댓값 0.000001 m 이하와 거부 행 번호의 정확한 일치를 요구할 수 있다. 기대값 0.250000 m에 결과 0.2500004 m이면 오차 0.0000004 m로 수치 조건을 통과하고, 0.250002 m이면 0.000002 m로 실패한다. 이 허용오차는 합성 계약이며 실물 작업의 허용 위치 오차로 쓰지 않는다. 허용오차를 만족해도 검사하지 않은 입력이나 장치 성능은 미확인이다.

최소 기록을 만들 때에는 소스 revision과 미커밋 변경, 의존성 명세의 식별자, 입력 데이터와 설정, 실행 환경·명령, 확인할 출력과 판정 기준을 서로 다른 항목에 적는다. 이후 “먼저 입력과 단위를 대조하고, 소스/설정 차이와 의존성 차이를 차례로 확인한다”처럼 비교 순서를 세운다. 모든 환경을 완벽하게 고정했다고 선언하기보다 미확인 영역을 분명히 남기는 편이 실제 원인 조사에 도움이 된다.

## 실습

다음 식별자는 실제 버전이나 hash가 아닌 **교육용 합성 이름**이다. 두 보고서를 같은 실험의 재실행이라고 주장하고 있다.

| 항목 | 보고서 A | 보고서 B |
|---|---|---|
| 소스 커밋 | RevA | RevA |
| 작업 트리 | 수정 없음 | 변환 함수 미커밋 수정 있음 |
| 패키지 잠금 기록 | LockA | LockB |
| 데이터 이름/내용 해시 | run.csv / DataA | run.csv / DataB |
| 컨테이너 태그/digest | lesson:stable / ImgA | lesson:stable / ImgB |
| 플랫폼·장치 드라이버 | 기록 있음 | 미기록 |
| native 산출물 | CPU 대상·ABI·빌드 옵션 기록 | 패키지 이름만 기록 |
| 가중치/전처리 통계 | WeightsA / StatsA | WeightsA / StatsB |
| 통계의 평균/표준편차 | 0.100 m / 0.050 m | 0.200 m / 0.100 m |
| 교정·좌표 설정 | CalibA·base 기준 | 미기록 |
| 출력 판정 | mm→m 변환 값 비교 | 성공 문구만 확인 |

1. 커밋 ID가 같아도 소스가 같다고 결론 낼 수 없는 이유와 추가로 남길 변경 기록을 적는다. 미추적 설정이 있었다면 어떻게 구분할지도 제안한다.
2. 소스 밖의 의존성·데이터·이미지·호스트 차이를 분류한다. 같은 태그나 파일명이 해결하지 못하는 차이를 설명한다. 250 mm 입력의 두 정규화 결과와 native·교정 기록의 미확인 범위를 적는다.
3. 보고서 B를 다시 확인하기 위한 명세를 항목별로 작성하고 비교 순서를 정한다. 정확히 일치시킬 출력 또는 허용 오차의 기준과 아직 검증하지 못한 범위도 적는다.

판정은 소스 상태·층별 환경 차이·재현 계획의 세 요소다. 도구를 실제 실행하지 않았다면 합성 기록 분석이라고 명시한다. 막히면 이름표가 같은 항목과 실제 내용 식별자가 다른 항목을 서로 다른 색으로 표시한다. 기존 파일을 지우거나 환경 전체를 재설치하는 명령은 필요하지 않다.

## 실습 해설

RevA가 같아도 B에는 실행에 반영될 수 있는 미커밋 수정이 있다. 실제 diff나 별도 변경 보관·검토 기록을 revision과 함께 남겨야 한다. 미추적 설정은 커밋에 포함된 것으로 가정하지 않고 비민감 설정 내용/식별자와 공급 방법을 적는다. LockA/B는 의존성 구성, DataA/B는 입력 바이트, ImgA/B는 이미지 내용의 차이다. 호스트 기록 누락은 같음을 입증할 정보가 없는 경우다. WeightsA는 같아도 StatsA/B로 정규화한 값은 3과 0.5로 다르다. native 대상·ABI·옵션과 실제 경로, 교정·좌표 설정도 확인해야 한다. 이처럼 소스 밖의 층과 실제 입력 의미를 분류하면 목표 2를 충족한다.

재현 명세는 먼저 사용할 소스 상태와 입력/단위·설정을 확정하고 의존성·이미지·플랫폼을 기록한 뒤 빌드/실행 명령과 관찰 기준을 정하는 식으로 작성할 수 있다. 예를 들어 250 mm 입력이 0.250 m로 변환되는지 수치까지 비교한다. 합성 허용오차 0.000001 m와 거부 행의 일치 기준을 먼저 정하고, 전처리가 포함되면 통계·축·단위도 재확인한다. “성공”이라는 문자열만 보고 값이 맞았다고 판정하지 않는다. 이 검사는 로그 변환 예제의 해당 입력 범위이며 실물 성능이나 모든 플랫폼의 동일 결과를 보장하지 않는다. 여러 순서도 가능한데 차이와 가설이 연결되어야 한다.

## 확인 문제

### Q1
두 실행이 같은 Git 커밋을 사용하고 한쪽만 미커밋 수정·미추적 설정을 갖는다. 같은 소스를 재현했다고 볼 수 있는가? 작업 트리·스테이징·커밋과 확인할 기록을 구분하라.

### Q2
컨테이너 digest와 패키지 잠금 기록이 같으면 입력 데이터·GPU 드라이버·모든 수치 결과도 자동으로 같다는 주장을 평가하라. 같은 가중치와 서로 다른 정규화 통계도 같은 입력을 보장하는지 평가하고 최소 두 가지 확인 대상을 제시하라.

### Q3
run.csv의 이름은 같지만 내용 해시가 달라졌다. 기존 로그 변환 실험을 재확인하기 위한 명세와 비교 절차, 결과 판정 기준을 작성하라. 해시만으로 확인하지 못하는 범위도 적어라.

## 해설

### Q1
그렇게 볼 수 없다. 작업 트리는 현재 파일 상태, 스테이징은 다음 기록에 넣을 상태, 커밋은 이미 기록한 상태다. 실제 실행한 변경과 미추적 설정을 별도로 대조해야 한다. 커밋 ID가 모든 작업 파일과 외부 설정을 포함한다고 생각하면 틀리다. 상태 이름만 나열하면 부분 답이며 실제 실행한 변경과 설정을 대조해야 한다.

### Q2
이미지와 잠금 기록의 범위 밖에 있는 입력 바이트·외부 연결 설정·호스트 드라이버·실행 플랫폼 등을 확인해야 한다. 수치 결과도 실행 조건·난수·병렬 처리와 비교 기준의 영향을 받을 수 있다. 가중치가 같아도 전처리 통계·축·단위가 다르면 모델 입력이 달라진다. native ABI/플랫폼과 교정·좌표 설정도 별도로 확인한다. 도구 하나를 사용했다는 사실만으로 재현 범위를 무제한 확장할 수 없다. 입력만 확인하면 부분 답이며 이미지 밖 조건과 비교 기준도 필요하다.

### Q3
사용할 데이터 내용과 공급 경로를 확정하고 헤더·단위·대표 행을 확인한다. 소스 상태·의존성·명령·환경을 기록해 같은 변환을 수행하고 정상값과 거부 행을 비교한다. 내용 해시의 동일성은 바이트 비교의 근거이며 측정 정확성·수집 조건·실물 안전을 입증하지 않는다. 파일명만 고정하는 답은 부족하다. 정상 변환만 적으면 부분 답이며, 거부 행·허용오차와 미확인 범위까지 명시해야 한다.
