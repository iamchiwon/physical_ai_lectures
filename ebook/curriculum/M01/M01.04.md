## 본문

### 도구와 산출물의 역할을 나눈다

AI/로봇 프로젝트는 Python 패키지뿐 아니라 native 확장, 메시지 생성물, 설정·모델 자산을 함께 사용한다. 빌드가 성공했다는 한 줄보다 어떤 소스와 의존성을 어떤 도구가 선택해 어떤 산출물을 만들었는지 알아야 한다. 일반 코드 작성 경험은 있어도 CMake와 colcon의 경계를 놓치면 환경 오류를 코드 오류로 오인하기 쉽다.

CMake는 타깃과 의존성·옵션을 기술한 프로젝트에서 선택한 생성기의 빌드 구성을 만든다. 타깃은 실행 파일이나 라이브러리 같은 논리적 빌드 단위다. 컴파일러는 소스를 번역하고, 링커는 필요한 정의를 연결한다. CMake가 그 도구들을 직접 대체하는 새 C++ 실행기는 아니다. [CMake 빌드 시스템 설명](https://cmake.org/cmake/help/v3.28/manual/cmake-buildsystem.7.html)은 타깃의 소스·사용 요구·링크 관계를 구분한다.

colcon은 workspace의 여러 패키지를 발견하고 의존 관계에 따라 빌드·시험을 조율하는 도구다. ROS의 CMake 기반 패키지는 ament_cmake가 등록·설치·의존성 내보내기 기능 등을 더한다. package.xml은 패키지 의존성·메타데이터를, CMakeLists.txt는 해당 빌드 요구를 담는다. 같은 ROS 패키지라도 여러 타깃을 가질 수 있다. 패키지 하나의 성공과 모든 타깃의 실행 검증은 같지 않다. Python 패키지 빌드도 있을 수 있으므로 모든 colcon 작업을 C++ 컴파일로 동일시하지 않는다.

### Configure·build·install·실행을 잇는다

configure는 소스·빌드 디렉터리, 생성기·컴파일러·의존성·옵션을 선택하고 빌드 구성을 만든다. 예를 들어 `cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug`는 단일 구성 생성기를 가정한 설정 예다. 다중 구성 생성기는 빌드 때 구성을 선택하는 등 차이가 있으므로 프로젝트 규약을 확인한다. 성공했다는 것은 이 단계의 설정이 만들어졌다는 뜻이며 소스의 모든 번역·링크 성공을 뜻하지 않는다.

`cmake --build build --target sensor_reader`는 그 빌드 공간의 지정 타깃을 빌드하는 명령 형태다. 실제 실행을 하려면 성공한 산출물과 실행 경로를 이어야 한다. install은 실행 파일·라이브러리·헤더·설정 등의 배포 위치를 준비하는 단계이며, 빌드 폴더의 결과와 실행 환경이 찾는 설치본은 다를 수 있다. 여기의 명령은 절차를 읽기 위한 예이며 실행할 소스 프로젝트나 ROS 실행 결과를 제공했다는 뜻은 아니다.

[colcon workspace 설명](https://colcon.readthedocs.io/en/released/user/what-is-a-workspace.html)의 기본 build·install·log는 각각 중간 빌드 자료, 설치 자료, 빌드 기록을 구분한다. 소스가 src에 있어도 실행이 install의 이전 결과를 선택할 수 있다. 파일 수정→대상 빌드 성공→필요한 설치 반영→실행 환경 선택→실제 실행·입출력 확인을 한 줄로 연결해 기록한다. configure만 반복하거나 실패 뒤 남은 실행 파일을 실행하면 수정 전 결과를 새 결과로 오인할 수 있다.

### 첫 실패의 층위를 찾는다

설정에서 `SensorMathConfig.cmake`를 찾지 못하면 우선 의도한 의존 패키지의 설치와 CMake 검색 경로·버전을 조사한다. 소스 함수의 계산식을 고칠 단계라는 근거는 없다. 설정 통과 뒤 `sensor.hpp: file not found`가 나오면 해당 번역 작업의 include 경로와 실제 헤더 위치, 타깃에 전달된 요구를 확인한다. 의존성이 기록돼 있다고 모든 소비 타깃에 필요한 헤더 경로가 전달됐다고 가정하지 않는다.

컴파일이 통과했는데 링크에서 `undefined reference to convert_mm`가 나오면 선언을 봤지만 필요한 정의와 맞게 연결하지 못했을 가능성을 조사한다. 타깃의 소스 목록과 링크 대상, 실제 라이브러리의 심벌·ABI·옵션을 확인한다. include 경로만 추가해서 실제 정의 누락까지 해결되는 것은 아니다. 의존 타깃의 요구를 소비 타깃에 연결하는 방식과 무관한 전역 경로 추가를 혼동하지 않는다.

링크 뒤 실행 시작에서 필요한 공유 라이브러리나 심벌을 못 찾으면 로더가 선택한 경로를 대조한다. 빌드 때 새 라이브러리를 썼어도 실행 때 오래된 설치본이 먼저 선택될 수 있다. 이때도 원문 오류와 실제 선택 경로가 단서이며 모든 로더 오류의 원인을 하나로 고정하지 않는다. 반대로 정상 시작 뒤 250 mm를 250 m로 표시했다면 빌드·로더 통과가 단위 계약까지 검증하지 않았다는 뜻이다. 입력 250 mm를 1000으로 나눈 0.250 m와 비교해 변환/소비 경계를 조사한다.

### Underlay·overlay와 빌드 캐시를 증거로 본다

CMakeCache.txt에는 선택한 도구·의존 경로·옵션 등이 남을 수 있다. 환경을 바꿔도 기존 빌드 공간이 이전 선택을 유지하는지 확인한다. 실패 기록을 보존하고 의도한 설정으로 분리된 빌드 공간을 만드는 것은 비교 방법이다. 모든 build/install 폴더를 먼저 삭제하면 어떤 조합에서 실패했는지 증거도 사라질 수 있다. 재구성을 할 때는 필요한 범위와 변경된 조건을 적는다.

ROS의 overlay가 같은 패키지를 대체한다면 헤더와 실행 라이브러리가 같은 계약을 사용해야 한다. [colcon overriding 안내](https://colcon.readthedocs.io/en/released/user/overriding-packages.html)는 include 검색 순서와 ABI 변경의 문제를 설명한다. 기반 라이브러리 ABI를 바꿨는데 그것을 사용해 이미 빌드한 패키지를 그대로 두는 문제는 실행 경로만 새 것으로 바꾸면 끝나지 않을 수 있다. 직접·간접 소비자와 필요한 재빌드 범위를 검토한다. 이번 활동은 실제 패키지를 교체하지 않는다.

예를 들어 소스 revision B를 편집했고 B의 configure가 성공했지만 build는 링크 오류로 끝났다고 하자. 이후 /old/install/sensor_reader의 build ID A가 출력됐다면 B의 계산이 검증됐다는 주장은 성립하지 않는다. B 빌드 실패와 A 실행을 서로 다른 사건으로 적는다. 다음 시도에서 B의 빌드·설치·선택 경로가 맞아도 합성 입력의 단위·출력, 실패 입력 거부, 실제 프로젝트의 실행 조건은 별도 검증이다. 빌드 성공은 물리 장비의 기한·정확도·안전을 증명하지 않는다.

## 실습

다음은 Ubuntu 24.04/Jazzy의 도구 역할을 가정한 합성 기록이다. 각 행은 독립 시도의 최초 실패이며 실제 CMake·ROS를 실행한 출력이 아니다.

| 시도 | 기록 |
|---|---|
| A | configure: SensorMathConfig.cmake를 찾지 못함 |
| B | configure 성공 → compile: sensor.hpp를 찾지 못함 |
| C | compile 성공 → link: undefined reference to convert_mm; 링크 목록에 정의를 제공하는 SensorMath 타깃 없음 |
| D | link 성공 → 시작 실패; 실행 로더는 /old/lib/libsensormath.so를 선택했고 필요한 새 심벌 없음 |
| E | 시작 성공 → 입력 250 mm, 표시 250 m; 기대 출력 계약은 m |

별도 재빌드 기록은 소스 B, configure 성공, sensor_reader 링크 실패, 그 뒤 실행 경로 /old/install/sensor_reader·build ID A다. 의도한 실행 경로는 /new/install/sensor_reader다.

1. CMake·컴파일러·링커·colcon의 역할과 패키지/타깃, configure/build/install/run을 나누어 쓴다.
2. A~E를 실패 층위로 분류하고 각 행의 다음 확인 하나를 제안한다.
3. 별도 기록에서 새 소스 B가 반영됐다는 주장을 평가하고 소스→구성→빌드→설치→실행→입출력 확인의 기록 계획을 만든다.

관찰은 역할표·최초 실패표·산출물 연결표로 남긴다. 막히면 가장 먼저 통과하지 못한 단계부터 읽는다. 삭제·설치·실제 명령 실행은 필요하지 않다.

## 실습 해설

CMake는 타깃의 빌드 구성을 만들고 컴파일러는 번역, 링커는 정의를 연결하며 colcon은 패키지 단위 작업을 조율한다. 패키지 안의 여러 타깃과 build/install/run의 근거를 나누면 목표 1 통과다. colcon을 C++ 컴파일러로 적으면 역할이 섞였다.

A는 의존성 발견/설정, B는 컴파일의 헤더 검색, C는 정의의 링크, D는 실행 로더/선택 라이브러리, E는 자료 의미 계약이다. 각각 패키지 설정 경로, include 요구, SensorMath 연결, 실제 라이브러리 경로와 ABI, 250/1000=0.250 m 변환·소비를 확인한다. 최초 실패와 다음 확인을 연결하면 목표 2 통과다. 오류 이름 암기만 하면 충분하지 않다.

B는 링크에 실패했고 실행된 것은 A다. 소스 revision·타깃/구성·의존성 경로와 빌드 성공, 설치 경로·실제 실행 build ID를 대조한다. 그 뒤 최소 입력의 출력과 오류 처리를 확인한다. overlay의 소비자 ABI와 재빌드 범위도 기록하면 목표 3 통과다. A의 출력 성공을 B의 수정 검증으로 쓰면 실패다.

## 확인 문제

### Q1
한 ROS 패키지에 실행 타깃 두 개가 있다. configure 성공과 한 타깃의 빌드 성공만으로 다른 타깃의 설치·실행도 완료됐다고 할 수 있는가? CMake와 colcon의 역할을 사용해 빠진 근거를 설명하라.

### Q2
헤더 선언은 찾았고 컴파일은 성공했지만 convert_mm의 정의를 연결하지 못했다. 어느 단계이며 무엇을 확인하는가? 이후 실행 시작도 성공했으나 100 mm가 100 m로 표시된다면 같은 문제라고 보아도 되는가?

### Q3
새 overlay의 ABI를 바꾸고 라이브러리만 빌드했다. 소비자는 이전 ABI로 빌드됐고 실행 경로도 이전 install이다. 어떤 불일치와 재검증 범위를 기록해야 하는가? 폴더를 모두 지우는 것만으로 해결을 입증할 수 있는가?

## 해설

### Q1
할 수 없다. CMake 타깃별 번역·링크와 필요한 설치, 실제 실행 경로·입출력 확인이 빠졌다. colcon의 패키지 조율과 타깃의 개별 작업을 구분한다. configure/build 차이만 적으면 부분 답이며 패키지 이름이 같으니 모든 타깃이 검증됐다는 답은 틀리다.

### Q2
링크 단계다. 정의를 포함하는 소스/라이브러리와 해당 타깃의 링크 관계·심벌/ABI를 확인한다. 이후 표시는 100/1000=0.100 m가 기대값이므로 단위 변환·소비 계약을 조사한다. 링크 성공이 의미 검증은 아니다. 단계만 맞으면 부분 답이고 헤더를 반복 추가하면 두 문제가 모두 해결된다는 답은 틀리다.

### Q3
소비자와 라이브러리의 ABI 및 실제 실행 설치본이 모두 불일치할 수 있다. 의도한 underlay/overlay, 선택 헤더·라이브러리, 직접·간접 소비자 재빌드 범위와 실제 실행 산출물·최소 입출력을 기록한다. 이전 실패 로그와 설정을 보존해 변경 조건을 비교한다. 경로만 고치면 부분 답이며 삭제 후 오류 문구가 사라졌다는 사실만으로 올바름을 입증할 수 없다.
