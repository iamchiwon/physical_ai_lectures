## 본문

### 빌드 명령을 파일마다 기억하지 않기

소스가 하나일 때는 컴파일러 명령에 파일명을 직접 넣을 수 있다. 파일과 라이브러리·옵션이 늘어나면 어떤 소스를 어느 실행 파일에 넣는지 기록해야 한다. CMake는 이런 빌드 요구를 기술하고 선택한 도구에 맞는 빌드 구성을 생성하는 도구다. 컴파일러를 대신하는 언어나 로봇을 실행하는 제어기가 아니다.

타깃(target)은 생성할 실행 파일이나 라이브러리 같은 빌드 단위를 나타낸다. 아래에서 contract_demo는 타깃 이름이고 contract.cpp는 그 타깃에 들어가는 소스다. `target_compile_features`는 이 타깃이 요구하는 언어 기능을 지정한다. [공식 명령 문서](https://cmake.org/cmake/help/latest/command/target_compile_features.html)는 타깃에 필요한 기능과 옵션을 연결하는 방식을 설명한다.

```cmake
cmake_minimum_required(VERSION 3.16)
project(M01Examples LANGUAGES CXX)
add_executable(contract_demo contract.cpp)
target_compile_features(contract_demo PRIVATE cxx_std_17)
set_target_properties(contract_demo PROPERTIES CXX_EXTENSIONS OFF)
```

3.16은 이 교육용 파일에 적은 최소 CMake 정책선이며 프로젝트 전체의 권장 최신 버전이나 모든 조합의 시험 완료를 뜻하지 않는다. `cxx_std_17`은 최소 C++17 기능을 요구한다. 같은 폴더의 CMakeLists.txt와 contract.cpp를 소스로 하여 별도 build 폴더를 만드는 흐름을 생각하면 된다. configure가 성공했다는 것과 소스가 빌드되었다는 것, 새 실행 파일을 실제로 실행했다는 것은 서로 다르다.

선택 실행에서는 준비된 도구로 `cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug`, 성공 뒤 `cmake --build build --target contract_demo`, 성공 뒤 `./build/contract_demo`를 순서대로 쓸 수 있다. 이는 일반적인 단일 구성 생성기 예이며 다중 구성 도구는 `--config Debug` 같은 선택을 확인해야 한다. 실패 뒤 예전 바이너리를 실행하지 않도록 각 단계 성공과 생성한 경로를 확인한다. 여기서는 실제 장비나 ROS 패키지를 빌드하지 않는다.

### 버그를 보기 전에 어느 값을 보는지 정하기

디버거는 정한 지점에서 실행을 멈추고 호출 위치·변수 등을 조사하는 도구다. 프로그램을 멈추어 본 값은 그 실행의 그 시점에 관한 증거다. 값이 예상과 다르면 입력 변환·호출 순서·다른 바이너리 실행 같은 가설을 나누어 조사한다. 처음 보인 숫자를 코드 전체의 진실로 일반화하지 않는다.

예를 들어 변환 함수에 들어오기 전 value=250, unit="mm"이고 반환값은0.25m인데 화면에는250m가 표시되었다면 어느 경계를 조사할까? 함수 입력이250이라는 사실만으로 변환 함수가 틀렸다고 결론 낼 수 없다. 반환값을 받은 호출자와 표시 단계의 변수·단위 라벨, 실제 실행한 바이너리/소스 대응을 확인해야 한다. 중단점은 함수 진입과 변환 뒤 소비 지점에 잡는 식으로 가설과 연결한다.

[LLDB 공식 튜토리얼](https://lldb.llvm.org/use/tutorial.html)은 중단점·실행·프레임 변수 관찰의 기본을 제공한다. 여기서는 실제 디버거 조작이 없어도 아래 합성 스냅샷을 해석하는 경로가 있다. 디버거로 멈춘 실행은 평소 타이밍을 바꾸므로 그 상태로 읽은 관찰을 주기성 측정으로 대신하지도 않는다.

### 메모리의 숫자를 보내면 의미도 함께 가는가

한 프로그램의 구조체는 메모리 안의 값 묶음이다. 그 메모리를 그대로 통신에 복사하는 것은 다른 언어나 컴퓨터가 같은 뜻으로 읽는다는 보장이 아니다. 필드 사이의 패딩, 정수 크기와 바이트 순서, 숫자 표현과 객체 수명이 고려되지 않을 수 있다. 특히 포인터 값은 다른 프로세스가 쓸 데이터 내용이 아니라 현재 실행의 주소 관계다.

직렬화(serialization)는 값을 전달·저장할 표현으로 만드는 일이다. JSON은 언어와 독립적인 텍스트 자료 표현 중 하나지만, [RFC8259](https://www.rfc-editor.org/rfc/rfc8259)가 설명하는 JSON 문법만 맞는다고 로봇의 단위·좌표·버전까지 정해지는 것은 아니다. 예를 들어 `{"version":1,"unit":"mm","position":250}`이라고 보낼 때 version과 unit의 의미, position의 허용 범위와 좌표 기준, 미지원 입력 처리도 애플리케이션 계약에 필요하다.

아래 예제는 JSON 바이트를 해석하는 파서가 아니다. 이미 파싱한 version·unit·value를 받아 version=1, unit=mm, 유한한 값만 수락해m로 변환하는 **계약 검증 함수**다. 지원하지 않는 단위를 추측하지 않고 결과 없음으로 돌려준다. 이번 함수는 길이의 유효 범위나 좌표·명령 안전성까지 검사하지 않는다.

```cpp
#include <cmath>
#include <iomanip>
#include <iostream>
#include <optional>
#include <string>

std::optional<double> decode_metres(int version, const std::string& unit,
                                    double value) {
    if (version != 1 || unit != "mm" || !std::isfinite(value)) {
        return std::nullopt;
    }
    return value / 1000.0;
}

int main() {
    const auto accepted = decode_metres(1, "mm", 250.0);
    const auto rejected = decode_metres(1, "m", 250.0);
    if (accepted) {
        std::cout << std::fixed << std::setprecision(3) << *accepted << " m\n";
    }
    std::cout << "unsupported unit accepted: " << std::boolalpha
              << rejected.has_value() << "\n";
}
```

`std::optional<double>`은 값이 있거나 없음을 표현한다. 실패를 숫자0으로 바꾸면 실제 원점과 거부를 구분하지 못하므로 사용자가 값 존재를 확인하게 한다. 기대 출력은 `0.250 m`, `unsupported unit accepted: false`다. 입력 문법·메타데이터·변환·소비 단계를 분리하면 다른 언어의 로그 처리기와 C++ 소비자가 어디서 뜻을 달리 읽었는지 추적하기 쉬워진다.

## 실습

기본은 코드·합성 스냅샷 읽기이며 선택 실행은 위 안전 계산만 수행한다.

1. contract_demo 타깃, 소스, configure/build/실행의 역할을 표로 만든다. contract.cpp를 고쳤는데 이전 출력만 보일 때 다음 확인할 두 가지를 적는다.
2. 합성 디버거 기록 “decode_metres 입력1/mm/250, 반환0.25; 호출자 표시250m”를 읽고 확인된 사실·오류 가설을 나눈다. 다음에 멈출 지점과 관찰할 변수를 제안한다.
3. (1,mm,250),(2,mm,250),(1,m,250),(1,mm,NaN)을 수락/거부하고 이유를 적는다. 이 필드들을 구조체 메모리 복사만으로 보내면 왜 계약이 부족한지 설명한다.

판정에는 빌드 흐름, 증거 기반 조사, 계약 판정 세 요소가 모두 필요하다. 막히면 변환 전 값과 변환 뒤 값에 단위를 붙여 다른 열에 쓰고, 값0과 값없음을 분리한다. 미지원 버전은 기존 버전처럼 가정하지 않는다.

## 실습 해설

configure는 빌드 구성을 만들고 build는 타깃을 생성하며 실행은 그 경로의 바이너리를 동작시킨다. 소스 변경 뒤 해당 타깃 재빌드 성공과 실제 실행 경로·소스 대응을 확인한다. 디버거 기록에서는 입력250mm와 반환0.25m가 맞아 변환 이후의 소비/표시 경로를 조사하는 것이 타당하다. 예를 들어 호출자에서 반환 optional의 값과 표시할 변수를 비교하고 단위 라벨을 확인한다. 다른 원인을 배제하지 않고 가설로 남긴다.

첫 입력만0.25m로 수락, 나머지는 버전·단위·유한성 조건으로 거부다. JSON 문법의 숫자가 맞아도 단위 계약은 여전히 필요하고, NaN은 JSON 표준 숫자 문법에도 속하지 않는다. 이번 함수는 파싱된 필드 계층에서도 그런 값을 거부한다. 메모리 복사는 패딩·표현·주소·단위 문제를 해결하지 않으므로 별도 표현과 계약을 정한다. 세 요소를 근거와 연결하면 충족한다.

## 확인 문제

### Q1
CMake configure가 성공했으므로 contract.cpp 수정도 실행에 반영되었다는 주장에 빠진 단계를 설명하라. 다른 실행 파일을 실수로 실행했는지 확인할 정보도 적어라.

### Q2
함수 진입의 value=250이라는 스냅샷만 보고 변환 결과가250m라고 결론 내릴 수 있는가? 변환 뒤 값이0.25인데 화면이250이면 다음 조사 지점과 단위 정보를 제안하라.

### Q3
(1,mm,−100)과(3,mm,100)을 이번 함수에 넣으면 어떻게 되는가? 첫 결과가 수락되었다고 실제 장비의 허용 위치라고 할 수 없는 이유와 raw struct 전송의 한계를 적어라.

## 해설

### Q1
configure 뒤 실제 타깃 build 성공과 새 바이너리 실행이 필요하다. 타깃의 소스 목록, 빌드 디렉터리·구성, 실행 경로와 소스 revision 등을 대조한다. configure만 반복하거나 실행 파일 이름만 같다는 이유로 반영을 확정하면 부족하다.

### Q2
진입값은 변환 전 단위mm일 수 있으므로 반환값과 단위를 관찰해야 한다. 호출자에서 optional을 읽은 값과 화면으로 넘긴 값, 라벨을 비교한다. 디버거가 어느 바이너리·소스에서 멈췄는지도 확인한다. 한 스냅샷으로 전체 코드의 오류 위치를 단정하지 않는다.

### Q3
첫 값은 유한하며 version1/mm이므로−0.1m로 수락되고 두 번째는 미지원 버전으로 거부된다. 함수에는 실제 작업 공간·좌표·장비 제한이 없으므로 수락은 이 변환 계약만의 결과다. 구조체 메모리의 패딩·표현·주소를 동일하게 해석한다고 가정하지 않고 명시적인 필드 표현을 정해야 한다.
