## 본문

### 터미널은 명령을 보내는 창이고 셸은 해석기다

터미널 창에 글자를 입력하면 셸(shell)이 명령 이름·인수·경로 등을 해석해 프로그램을 실행한다. 프로그램이 새로 실행된다는 것과 셸 자체가 바뀐다는 것은 다르다. 셸이 작업 중인 위치를 현재 디렉터리라고 한다. `pwd`는 그 위치를 보여 주고, 상대 경로는 그 위치를 기준으로 해석한다. `/work/project/data/log.csv`처럼 처음부터 `/`로 시작하는 경로는 절대 경로다.

예를 들어 현재 위치가 `/work/project`이면 `data/log.csv`는 프로젝트 안의 파일을 가리킨다. 현재 위치가 `/work`이면 같은 문자열은 다른 위치를 가리킨다. 프로그램 파일이 올바르게 존재해도 입력 파일을 현재 위치 기준으로 찾다가 실패할 수 있다. 따라서 “파일이 없다”는 오류를 보면 설치 문제로 결론 내리기 전에 어느 경로를 찾았는지 확인한다.

공백이 있는 파일명은 인수 경계를 주의한다. 셸에서 `python3 "log reader.py"`는 공백이 포함된 이름 하나를 인수로 넘기는 표현이다. 따옴표 없이 쓰면 프로그램에 `log`와 `reader.py`라는 별도 인수가 갈 수 있다. 이는 파일명을 고치기보다 셸이 나눈 인수를 확인해야 하는 문제다. [GNU Bash 매뉴얼](https://www.gnu.org/software/bash/manual/bash.html)은 셸의 인수 해석·인용과 종료 상태를 설명한다. 이 단위에서는 알 수 없는 명령을 복사해 실행하지 않고 기록을 읽는다.

### 프로세스가 있다는 것과 일이 끝났다는 것

실행 중인 프로그램의 한 인스턴스를 프로세스라고 하며 운영체제는 PID라는 식별 번호를 부여한다. 같은 프로그램을 두 번 실행하면 이름은 같아도 PID가 다를 수 있다. 프로세스 목록에 이름이 보이는 것은 실행 중이라는 단서이지 센서가 정상 수신되거나 포트가 열렸다는 증거는 아니다.

프로그램은 끝날 때 종료 상태를 남긴다. 일반적으로0은 성공,0이 아닌 값은 실패를 나타내는 관례지만 정확한 의미는 해당 프로그램의 계약에 달려 있다. 종료 코드만 보고 고장 원인을 단정하지 말고 오류 메시지·입력 경로·직전 작업을 함께 읽는다. 계속 실행되는 수집기나 서버는 아직 종료하지 않았으므로 “종료 코드0을 얻지 못했다”가 곧 실패라는 뜻도 아니다. 프로세스의 생존, 작업 결과, 오류 기록을 다른 칸에 둔다.

### USB가 보인다는 말에는 여러 단계가 있다

USB 센서를 연결하면 물리적 연결, 운영체제의 장치 인식, 드라이버 연결, 프로그램의 장치 열기가 서로 다른 단계에서 성공하거나 실패할 수 있다. 어떤 장치는 `/dev/ttyACM0` 같은 장치 노드로 보이지만 모든 USB 장치가 같은 이름을 갖는 것은 아니다. 번호나 경로가 같아 보이는 것만으로 같은 물리 장치라고 확정하지도 않는다. 이 단위의 경로는 합성 사례다.

Ubuntu의 파일·장치 권한은 소유자와 그룹 등을 통해 접근을 제어한다. 예시 `crw-rw---- root dialout /dev/ttyACM0`에서 맨 앞의 c는 문자 장치, 뒤의 권한은 소유자·그룹·기타 순서다. 소유자 root와 그룹 dialout은 읽기/쓰기 권한이 있고 기타에는 없다. 사용자가 해당 소유자도 아니고 허용된 그룹에도 속하지 않는다면 이 권한 기록은 접근 거부의 유력한 설명이 된다. 다만 실제 접근에는 장치 정책·다른 프로세스 점유 등 추가 조건도 있어 권한표 하나가 모든 원인을 설명하는 것은 아니다.

권한 오류를 만났다고 프로그램 전체를 관리자 권한으로 실행하거나 모든 사용자에게 쓰기를 허용하는 것은 기본 해결법이 아니다. 먼저 정확한 장치와 사용자·그룹을 확인하고 필요한 최소 권한과 운영 절차를 검토한다. [Ubuntu의 사용자·그룹 안내](https://ubuntu.com/server/docs/how-to/security/user-management/)는 계정과 권한 관리의 기본을 설명한다. 이 활동에서는 그룹 변경·권한 변경·실물 명령을 수행하지 않는다.

### 네트워크는 '프로세스 있음' 다음에 확인한다

서버 프로세스가 데이터를 받으려면 주소와 포트에 묶여 대기해야 한다. 포트는 같은 호스트 안에서 통신 대상을 구분하는 번호다. 클라이언트가 접속하는 주소·포트와 서버가 실제 대기하는 주소·포트를 대조해야 한다. `127.0.0.1`은 현재 네트워크 환경 자신을 가리키는 loopback 주소다. 다른 컴퓨터나 별도 컨테이너에서 같은 주소를 쓰면 원래 서버 컴퓨터를 가리키는 것으로 단정할 수 없다.

같은 컴퓨터의 서버가 `127.0.0.1:5000`에서 대기하는데 클라이언트가 `127.0.0.1:5001`을 찾는다면 포트 불일치를 먼저 조사한다. 이 경우 USB 권한을 바꾸어도 대상 포트는 맞지 않는다. 서버 대기 상태를 읽는 `ss` 같은 도구의 출력도 어떤 통신 종류와 주소를 표시하는지 확인해야 한다. 연결 거부는 해당 대상에 적절한 대기가 없다는 등의 가능성을, 시간 초과는 경로·방화벽·응답 지연 등 다른 가능성을 제시하지만 메시지 하나로 원인을 모두 확정할 수는 없다.

좋은 조사 순서는 무엇을 기대했는지 적고, 실행 위치→파일/장치→프로세스 상태→실제 endpoint→연결 기록을 차례로 대조하는 것이다. 매번 모든 단계를 고치는 대신 오류가 나타난 계층의 가설을 하나씩 확인한다. 로봇의 움직임을 시험하기 전에 읽기 전용 자료로 원인을 좁힐 수 있는 경우가 많다.

## 실습

다음은 Ubuntu24.04를 가정한 **교육용 합성 출력**이며 이 컴퓨터에서 실행한 결과가 아니다. 장비나 설치 없이 표만 읽는다.

| 기록 | 내용 |
|---|---|
| 현재 위치 | `/work` |
| 기대 파일 | `/work/project/data/run.csv` |
| 실행 인수 | 프로그램이 `data/run.csv`를 열려고 함 |
| 오류 | 파일 경로 없음, 프로그램 종료 상태2 |
| 실행 사용자 | `learner`(비관리자) |
| 사용자 그룹 | `learner` |
| 장치 권한 | `crw-rw---- root dialout /dev/ttyACM0` |
| 장치 오류 | `/dev/ttyACM0` 열기: 접근 거부 |
| 서버 기록 | PID420가 살아 있으며 TCP `127.0.0.1:5000` 대기 |
| 클라이언트 | 같은 호스트에서 TCP `127.0.0.1:5001` 연결 시도 |

1. 프로그램이 실제로 찾은 파일 경로를 적고, 기대 경로와 다르게 된 이유를 설명한다. 종료 상태2의 의미를 무엇까지 말할 수 있는지도 적는다.
2. 장치 존재와 프로그램 접근을 분리하고, 권한표·그룹 기록에서 접근 거부를 설명할 근거와 추가 확인 하나를 적는다.
3. 서버 PID가 있다는 사실과 대기 endpoint를 구분한다. 연결 대상의 불일치를 찾고 관리자 권한 확대보다 먼저 확인할 항목을 적는다.

판정은 세 계층마다 사실·가설·다음 확인을 구분하는 것이다. 정답이 막히면 상대 경로 앞에 현재 위치를 붙이고, 권한의 세 묶음과 주소/포트 두 값을 각각 표시한다. 실제 시스템 변경 명령은 제출하지 않는다.

## 실습 해설

파일은 `/work/data/run.csv`를 찾았으므로 기대한 프로젝트 경로와 다르다. 현재 위치를 프로젝트로 맞춘 뒤 적절한 상대 경로를 쓰거나 올바른 절대 경로를 전달하는 방안을 검토할 수 있다. 종료 상태2는 이 프로그램에서 실패했다는 기록과 함께 읽으며, 모든 프로그램의2가 동일한 뜻이라고 일반화하지 않는다.

장치 노드는 존재하지만 learner는 제시된 허용 소유자·그룹과 일치하지 않는다. 이는 접근 거부의 근거다. 먼저 실제 장치 식별과 실행 사용자의 그룹, 필요한 접근 권한을 확인한다. 단순 재설치나 무제한 권한 부여가 논리적으로 도출되지는 않는다. 서버는 살아 있고5000에서 대기하지만 클라이언트는5001을 찾는다. 같은 호스트/통신 종류인지 확인한 뒤 설정한 대상 포트를 대조한다. 한 단계의 오류를 다른 단계의 권한 변경으로 덮으려 하지 않는 설명이면 충족한다.

## 확인 문제

### Q1
현재 위치가 `/work/project/tools`이고 입력이 `../data/a.csv`다. 가리키는 위치는 어디인가? 수집기 PID가 보인다는 것만으로 이 파일 처리 성공을 주장할 수 없는 이유는?

### Q2
장치 권한은 같지만 사용자가 dialout 그룹에도 속한다고 새로 확인했다. 이제 장치 통신 성공을 확정할 수 있는가? 추가 확인 두 가지와 무분별한 관리자 실행의 문제를 적어라.

### Q3
서버는 한 컴퓨터의 `127.0.0.1:7000`에 대기하고 다른 컴퓨터의 클라이언트도 `127.0.0.1:7000`을 사용한다. 숫자가 같아도 연결 대상이 달라질 수 있는 이유와 먼저 확인할 사항을 설명하라.

## 해설

### Q1
`..`는 한 단계 위이므로 `/work/project/data/a.csv`다. PID는 실행 인스턴스의 생존에 관한 기록이며 파일을 열고 원하는 레코드를 처리했는지는 결과·오류 로그를 읽어야 한다. 경로 계산과 성공 근거를 함께 설명한다.

### Q2
그룹 권한의 한 조건을 충족했을 뿐이다. 실제 장치가 맞는지, 드라이버·설정과 다른 프로세스 점유가 어떤지 등을 조사한다. 전체 프로그램을 높은 권한으로 실행하면 필요 없는 접근 범위까지 넓히고 원인을 가릴 수 있다. 권한을 더 주면 항상 해결된다는 답은 부족하다.

### Q3
loopback은 각 컴퓨터 자신을 가리키므로 두 호스트의 endpoint는 다르다. 서버 실행 위치와 수신 주소·포트, 클라이언트가 의도한 서버 호스트와 접근 경로를 확인한다. 실제 장비 네트워크를 임의로 노출하거나 방화벽을 전부 끄는 것은 이 정보로 정당화되지 않는다.
