## 본문

### C와 C++는 같은 이름의 모드가 아니다

C와 C++는 관련이 깊지만 서로 다른 언어다. 어떤 문법이나 표준 라이브러리를 쓰는지, 어떤 표준 모드로 번역하는지 밝혀야 한다. C++ 코드를 C 컴파일 모드로 해석하면 같은 파일처럼 보여도 오류가 날 수 있다. 이 단위의 실행 예제는 C++17이며 C 예제로 그대로 컴파일할 수 있다고 주장하지 않는다. 이후 C를 쓰는 드라이버나 MCU 자료를 만날 때에는 해당 언어와 버전을 다시 확인한다.

프로그램의 값은 실행 중 객체에 저장된다. 예를 들어 한 측정에 시각과 위치가 필요하다면 따로 떠다니는 숫자 두 개 대신 `Sample`이라는 구조체(struct)로 묶을 수 있다. 구조체는 서로 관련된 필드의 이름과 타입을 정한다. `sample.position_m`은 sample의 위치 필드에 접근한다는 표현이다. 이름에 m을 넣은 것은 단위 계약의 단서이며 컴파일러가 자동으로 mm와 구별해 준다는 뜻은 아니다.

### 값 복사와 같은 객체 보기

함수 인수 `Sample sample`은 이번 예에서 호출자가 준 값을 별도 객체로 받는 값 전달이다. 함수 안에서 이 복사본의 위치를 바꾸어도 호출자 current의 필드가 자동으로 바뀌지 않는다. 반환한 값을 새 객체 next에 저장하면 이전 값과 계산 결과를 나란히 보관할 수 있다. 큰 자료에서는 복사 비용도 고려하지만, 의미를 이해하기 전에 모든 값을 포인터로 바꿀 필요는 없다.

포인터는 어떤 객체를 가리키는 값을 가진다. `&current`는 current를 가리키는 포인터를 얻는 표현이고, `*view`는 view가 가리킨 객체를 통해 접근하는 간접 참조다. `const Sample* view`는 이 포인터를 통해 가리킨 Sample을 수정하지 않는다는 제한을 둔다. 그러나 다른 경로에서 객체가 바뀌지 않는다고 보장하거나 객체의 수명을 늘리는 것은 아니다.

참조를 받는 `const Sample&`도 이번 함수에서는 기존 객체를 읽는 비소유 접근이다. 객체를 복사해 소유하는 값과 잠시 바라보는 참조/포인터를 구분하자. 같은 숫자0.1을 출력해도 “복사된 값”과 “그 객체를 읽은 값”은 이후 갱신·수명에서 다르게 동작할 수 있다.

```cpp
#include <iomanip>
#include <iostream>

struct Sample {
    double stamp_s;
    double position_m;
};

Sample shifted(Sample sample, double dx_m) {
    sample.position_m += dx_m;
    return sample;
}

double position_of(const Sample& sample) {
    return sample.position_m;
}

int main() {
    Sample current{0.0, 0.1};
    const Sample* view = &current;
    Sample next = shifted(current, 0.02);
    std::cout << std::fixed << std::setprecision(3)
              << position_of(*view) << " " << next.position_m << "\n";
}
```

current와 next는 각각0.100m와0.120m다. `std::fixed`와 `std::setprecision(3)`은 이번 출력의 소수점 형식을 정할 뿐 내부 계산을 정확한 십진수로 바꾸는 기능은 아니다. 위 코드에서 view를 읽는 동안 current는 main 안에서 살아 있다. 로봇 장치나 파일을 열지 않는 작은 값 계산이다.

### 주소가 남아 있다고 객체가 살아 있는 것은 아니다

이 예제처럼 static을 붙이지 않은 자동 저장 기간 지역 객체의 수명은 그 실행 범위와 관련된다. 그런 객체를 가리키는 포인터나 참조를 밖으로 돌려주고, 함수가 끝난 뒤 그 객체를 읽으려 하면 유효한 객체 접근이 아니다. static 등 다른 저장 기간의 객체는 규칙이 다르므로 “함수 안에 선언했다”는 위치만으로 수명을 판정하지 않는다. 메모리 주소처럼 보이는 숫자가 남거나 우연히 원하는 출력이 나와도 올바름을 입증하지 못한다. 이런 수명 위반은 정의되지 않은 동작(Undefined Behavior, UB)을 만들 수 있다. 이 단위는 위험한 버전을 실행해 결과를 관찰하도록 요구하지 않는다.

[C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f43-never-directly-or-indirectly-return-a-pointer-or-a-reference-to-a-local-object)는 지역 객체의 포인터/참조 반환 같은 수명 문제를 다룬다. 해결을 고민할 때에는 필요한 값만 반환할지, 호출자가 소유한 객체를 정해진 기간 읽을지, 소유권을 표현하는 컨테이너나 자원 관리 방식을 쓸지 구분한다. `new`를 추가해 주소를 오래 살려 놓으면 책임 문제가 자동으로 해결된다고 생각해서도 안 된다.

배열 범위·컨테이너 변경·다른 스레드의 갱신도 포인터 유효성과 데이터 해석에 영향을 줄 수 있다. 이번 예제에는 동적 배열 확장이나 동시 접근을 넣지 않았다. 작은 안전 예제가 성공했다고 모든 포인터·공유 데이터 사용이 안전하다고 일반화하지 않는다.

### 소스에서 실행까지는 한 단계가 아니다

컴파일은 소스의 문법·타입 등을 검사하고 번역하는 과정이다. 링크는 사용한 함수·변수 정의와 필요한 라이브러리를 연결해 실행 파일 등을 만드는 단계다. 헤더의 선언을 보고 코드를 번역할 수 있어도 함수의 실제 정의가 링크 대상에 없으면 링크 오류가 날 수 있다. 실행 파일이 만들어져도 잘못된 단위·수명·입력 계약은 실행 중 문제를 일으킬 수 있다.

선택 실행에서는 코드를 `sample_value.cpp`로 저장하고, 이미 준비된 C++17 도구로 표준 모드를 명시해 빌드한다. 예를 들어 Clang 환경의 `clang++ -std=c++17 -Wall -Wextra -pedantic sample_value.cpp -o sample_value`는 이 파일을 실행 파일로 만드는 한 방법이다. 경고를 읽고 원인을 확인하되, 경고가 없다고 UB나 논리 오류가 모두 없다는 뜻은 아니다. 빌드에 성공한 경우에만 `./sample_value`로 실행한다. 예를 들어 위 빌드 명령 뒤에 `&& ./sample_value`를 붙이면 앞 명령 성공 때만 실행하며, 컴파일 실패 뒤 예전 실행 파일을 새 결과로 오인하는 일을 줄일 수 있다. 출력이 `0.100 0.120`인지 확인하고 실제 운영체제·컴파일러·옵션을 함께 기록한다. 이 명령은 장비의 주기성이나 ROS 패키지 빌드를 검증하지 않는다.

## 실습

기본 경로는 위 코드의 종이 추적이다. 이미 컴파일러를 갖춘 경우 안전 예제만 실행해 예상과 비교할 수 있다.

1. current, 함수 인수 sample, next, view가 각각 값 객체인지 비소유 접근인지 표시한다. shifted 호출 전후 current/next의 위치를 적고, 이 코드가 C++17인지 C인지 밝힌다.
2. “함수 내부에서 static 없는 자동 저장 기간의 Sample temp를 만들고 그 주소를 반환한 뒤 호출자가 읽는다”는 설계의 위험 구간을 선으로 표시한다. 위험한 코드를 실행하지 않고, 필요한 값을 반환하는 대안을 문장으로 제안한다.
3. “문법 오류”, “선언된 함수 정의가 링크 대상에 없음”, “실행 뒤 m/mm 의미가 다름”을 컴파일·링크·실행/계약 검토로 분류한다. 선택 실행을 했다면 안전 예제 출력과 환경·한계를 남긴다.

판정은 값/참조 추적, 수명 근거, 단계별 오류·검증 기록의 세 요소다. 막히면 객체마다 만들어진 범위와 마지막으로 읽는 지점을 적는다. 주소 숫자를 출력하는 실험이나 UB 실행으로 안전성을 판정하지 않는다.

## 실습 해설

current·sample·next는 별도 값 객체이고 view는 current를 보는 포인터다. shifted는 복사본의0.1에0.02를 더해0.12를 반환하므로 current는0.1을 유지한다. position_of는 참조받은 살아 있는 객체에서 위치 값만 반환한다. 코드에는 C++ 스트림·참조가 쓰이며 C 소스로 동일하게 취급할 수 없다.

위험 설계에서는 자동 저장 기간인 temp가 함수 종료 뒤 수명을 끝냈는데도 호출자가 그 객체를 읽으려는 지점이 문제다. 필요한 Sample을 값으로 반환하고 호출자가 그 결과를 보관하는 방식이 이 작은 과제의 대안이다. 문법 오류는 컴파일, 정의 누락은 링크, 단위 의미는 실행 결과와 데이터 계약의 문제다. 실제 실행을 하지 않았다면 예상 출력이라고 쓰면 된다. 실행했어도 다른 환경·장비·병렬 접근까지 검증했다고 쓰지 않으면 세 요소를 충족한다.

## 확인 문제

### Q1
current의 위치0.1에 대해 `shifted(current, -0.03)`의 반환값을 next에 넣는다. current와 next의 위치를 구하고, view가 current를 가리킬 때 어느 값을 읽는지 설명하라. 이 예제를 C 코드와 같은 것으로 볼 수 없는 이유도 적어라.

### Q2
`const` 포인터가 static 없는 자동 저장 기간의 지역 객체를 가리키면 함수 종료 뒤에도 안전하다는 주장을 평가하라. 실행 없이 수명 관계를 점검하는 방법과 이 과제의 값 반환 대안을 설명하라.

### Q3
함수 선언 헤더는 찾았지만 실행 파일을 만들 때 정의를 찾지 못했다. 어떤 단계의 문제인가? 이를 고친 뒤 출력이 나와도 단위·수명·주기성이 모두 맞다고 할 수 없는 이유는?

## 해설

### Q1
current는0.1, next는0.07이고 view는 살아 있는 current의0.1을 읽는다. 값 전달과 반환 결과를 원본 수정으로 혼동하면 틀리다. C++17 참조·스트림 등 사용 언어와 표준 라이브러리 계약이 있어 별도 C 컴파일 모드와 같지 않다.

### Q2
const는 그 접근 경로의 수정 제한이지 객체의 생존 보장이 아니다. 객체 생성/범위 종료와 포인터의 사용 지점을 시간 순으로 적어 수명 종료 뒤 접근을 찾는다. 필요한 데이터를 값으로 반환해 호출자가 소유하게 하는 대안을 제안할 수 있다. 우연히 값이 읽혔으므로 괜찮다는 판단은 UB의 의미를 놓친 것이다.

### Q3
선언과 번역 이후 실제 정의를 연결하지 못하는 링크 단계의 문제다. 연결 대상을 확인해야 하며 헤더를 반복 복사하는 것으로 해결되지 않을 수 있다. 성공한 출력 한 번은 그 조건의 결과일 뿐, 의미상 단위나 모든 수명 경로·스케줄링 특성을 증명하지 않는다.
