## 본문

### 실행 계획과 준비 조건은 다른 정보다

Launch는 여러 실행물과 설정을 한 실행 계획으로 기술하는 도구다. 패키지·실행 파일·노드 이름·네임스페이스·파라미터·remap 등의 정보를 모아 반복 가능한 구성을 만든다. Python/XML/YAML 형식이 사용될 수 있지만 Launch 파일의 형식과 노드의 파라미터 YAML 파일을 같은 것으로 보지는 않는다. 전자는 무엇을 어떻게 시작할지, 후자는 해당 노드에 어떤 설정값을 줄지를 기술한다. 파일을 묶었다고 모든 노드의 초기화 완료나 데이터 준비 순서가 자동으로 보장되지는 않는다.

예를 들어 센서 프로세스의 시작 사건은 실행이 시작되었다는 증거다. 센서 데이터가 유효하고 프레임 변환이 준비되었다는 증거는 아니다. 일정 시간 기다리는 sleep을 넣으면 이 차이를 숨길 수 있지만 느린 기동이나 실패가 생겼을 때 준비를 판정하지 못한다. 필요한 조건을 ‘구성 전이 성공’, ‘유효한 첫 관측 수신’, ‘요청한 시각의 변환 존재’처럼 관찰 가능하게 적고 시간초과와 실패 처리를 정의한다. 프로세스 종료를 감시하거나 재시작하는 정책도 무조건 반복하면 원인과 상태를 잃을 수 있으므로 재시도 횟수와 중단 조건을 남긴다.

가상 Launch가 namespace=/robot_a, name=checker인 노드를 만들면 최종 노드 이름은 /robot_a/checker다. 다음 파라미터 파일의 대상이 /checker라면 그 이름과 다르다. 이 예에서는 와일드카드도 없고 다른 설정 덮어쓰기도 없다고 가정하므로 원하는 노드에 이 항목이 적용되었다고 볼 수 없다.

```yaml
/checker:
  ros__parameters:
    stale_limit_ms: 100
```

대상을 /robot_a/checker로 맞추는 것이 이번 예의 수정이다. 단, 파일 수정만으로 선언·검증·적용 성공을 모두 입증한 것은 아니다. 노드의 실제 현재값과 적용 응답, 사용하는 파일의 버전을 확인한다. 같은 경로의 옛 파일이나 이후의 덮어쓰기가 있으면 화면에 보이는 파일과 실제 설정이 달라질 수 있다. [공식 Launch 구성 자료](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Tutorials/Intermediate/Launch/Using-ROS2-Launch-For-Large-Projects.rst)는 노드 이름·설정 범위·와일드카드를 함께 설명한다.

### Lifecycle은 준비 절차를 드러내는 상태기계다

관리 노드(LifecycleNode)는 구성과 활성화 등의 상태 전이를 명시하는 인터페이스를 제공한다. 대표 주요 상태는 unconfigured(미구성), inactive(구성했으나 비활성), active(활성), finalized(종결)다. configuring이나 activating 같은 전이 상태에서 콜백이 실행되고 그 결과에 따라 다음 주요 상태를 정한다. 일반 노드가 모두 이 구조를 자동으로 갖는 것은 아니다.

단순 성공 경로는 unconfigured→configure→inactive→activate→active다. configure가 실패를 반환하는 경로는 성공한 inactive와 구별하며 기본 상태기계에서는 unconfigured로 돌아갈 수 있다. error 처리와 failure 반환은 구별해야 한다. deactivate는 active에서 inactive로, cleanup은 inactive에서 unconfigured로 돌아가 자원을 정리하는 경로다. finalized는 종결 상태이며 그 객체를 다시 activate해서 재사용하는 상태가 아니다. 전이 요청 수락·전이 콜백 결과·현재 상태를 각각 기록하면 어디까지 준비되었는지 알 수 있다.

가상 동일 시계에서 프로세스 시작은 0 ms, configure 시작은 10 ms, 성공 종료는 50 ms, activate 시작은 60 ms, 성공 종료는 70 ms라고 하자. 구성 처리 40 ms, 두 전이 사이 대기 10 ms, 활성화 처리 10 ms다. 시작부터 active까지 70 ms지만 그 안의 구성과 활성화 처리 합계는 50 ms다. 두 수치를 같은 지연이라고 부르지 않는다. configure가 실패했다면 뒤의 active 도달을 예정표만으로 채우지 않는다.

중요한 한계도 있다. Lifecycle 상태 이름만으로 모든 사용자 타이머·구독·일반 발행이 자동 차단되지는 않는다. Jazzy C++의 LifecyclePublisher는 활성 상태를 검사하여 발행하지만, 사용자가 만든 별도 작업과 외부 스레드에는 적절한 상태 검사가 필요하다. [공식 lifecycle 예제](https://github.com/ros2/demos/blob/jazzy/lifecycle/README.rst)의 발행 제어를 모든 응용 코드의 보편적 차단이나 실물 안전 기능으로 과장하지 않는다. active는 필요한 구성 절차를 통과한 상태이지 센서 정확도·전원·실행기 안전의 최종 보증이 아니다.

### 로그가 말하는 것과 말하지 않는 것

ROS 로그의 심각도는 DEBUG, INFO, WARN, ERROR, FATAL 순서다. 설정한 수준보다 낮은 메시지는 출력 대상에 전달되지 않을 수 있다. ERROR 기준에서는 INFO의 ‘구성 완료’ 기록이 보이지 않는 것이 정상일 수 있다. 로그는 콘솔·파일·/rosout 등의 대상으로 갈 수 있고 대상별 비활성화나 필터도 가능하다. 따라서 ‘화면에 오류가 없다’는 관찰은 오류가 없었다는 결론과 다르다. 메시지를 생성하는 코드 경로가 실행됐는지, 로거와 출력 대상의 설정이 무엇인지 확인한다.

진단 메시지는 구성요소의 상태와 설명·관련 값을 정해진 구조로 전달하는 데 쓰인다. DiagnosticStatus의 OK/WARN/ERROR/STALE은 로그의 DEBUG~FATAL 체계와 별도다. STALE은 오래되거나 갱신되지 않은 상태를 표현하는 데 쓰일 수 있으며, 숫자 수준만 보고 전원 고장 같은 원인을 확정하지 않는다. 진단을 만든 노드의 판단 규칙과 마지막 갱신 시각이 필요하다. 가상 마지막 갱신 200 ms, 현재 350 ms면 나이는 150 ms다. 이 응용이 한계를 100 ms로 정의하고 나이>한계일 때 stale로 분류한다면 조건을 넘는다. 다른 노드에도 이 규칙이 자동 적용되는 것은 아니다.

복구 계획은 기록을 지우고 다시 시작하는 것으로 끝나지 않는다. 설정 버전과 실패 상태를 보존하고, 무엇이 유효해졌을 때 다시 구성/활성화할지 적는다. [기존 1장의 관측과 제어 예제](/textbook/01_physical_ai_isaac_ros2--chapter-10/)에도 같은 관점을 적용하여 프로세스가 살아 있음·통신 상태·관측 유효성·명령 허용을 따로 본다.

## 실습

가상 Launch는 /robot_a/checker를 만들지만 파라미터 파일의 대상은 /checker다. 의도한 stale_limit_ms는 100이다. Lifecycle 기록은 본문의 0/10/50/60/70 ms 성공 경로를 사용한다. 실제 현재 파라미터 조회와 로그의 출력 대상은 아직 모른다. 마지막 진단 갱신은 200 ms, 판단 시각은 같은 시계의 350 ms이며, 응용의 stale 규칙은 나이>100 ms다. 콘솔의 로그 수준은 ERROR다.

1. 파라미터 대상의 불일치를 찾고 이번 조건에서 수정할 이름을 적는다. 프로세스가 시작됐다는 기록만으로 설정과 준비가 끝났다고 할 수 없는 이유를 설명한다.
2. 각 전이 뒤의 주요 상태를 쓰고 구성·대기·활성화 처리 시간과 시작부터 active까지를 계산한다. configure가 failure를 반환한 변형에서 무엇을 확인해야 하는지 적는다.
3. 진단 나이와 stale 여부를 계산한다. INFO 기록이 콘솔에 없다는 사실과 오류가 없다는 결론을 구분하고, 다음에 확인할 증거 두 가지와 재활성화 조건을 제안한다.

관찰 대상은 가상 설정과 상태 기록이다. 실제 활성화 요청은 보내지 않는다. 막히면 ‘요청·전이 결과·현재 상태’를 세 칸으로 나눈다. 진단 시각의 시계가 다르면 바로 빼지 않고 비교 가능 여부부터 확인한다.

## 실습 해설

파일의 대상을 /robot_a/checker로 맞춰야 한다. 실제 설정의 수락과 현재값은 아직 별도 확인 대상이다. 프로세스 시작은 초기화 완료와 다른 사건이다.

configure 성공 뒤 inactive, activate 성공 뒤 active다. 구성은 50−10=40 ms, 대기는 60−50=10 ms, 활성화는 70−60=10 ms, 시작부터는 70 ms다. configure가 failure를 반환하면 성공 경로를 이어 적지 않고 전이 결과와 현재 상태를 조회한다. 기본 상태기계의 해당 실패 경로와 응용의 오류 처리를 구분한다.

진단 나이는 350−200=150 ms로 한계 100 ms를 넘는다. ERROR 필터에서 INFO가 보이지 않는 것은 출력 설정과 맞으므로 구성 실패를 단정할 수 없다. 로거/출력 대상 설정·실제 현재 파라미터·전이 응답과 상태·진단 갱신을 확인한다. 재활성화는 실패 원인과 준비 조건을 확인한 뒤 성공 전이 및 새 유효 자료를 근거로 판단한다. 이름/준비 조건, 상태/시간 계산, 로그/진단 증거의 세 항목을 모두 설명하면 통과다.

## 확인 문제

### Q1
최종 노드 이름이 /r2/checker인데 YAML은 /checker를 대상으로 한다. 와일드카드가 없는 경우 설정 적용을 어떻게 확인하는가? Launch의 프로세스 시작 사건과 준비 완료는 왜 다른가?

### Q2
가상 configure가 5~25 ms에 성공하고 activate가 30~38 ms에 성공한다. 주요 상태와 각 처리·대기 시간을 구하라. inactive라는 이름만으로 모든 사용자 구독 콜백이 차단됐다고 할 수 있는가?

### Q3
WARN 이상만 출력하는 콘솔에 INFO가 없고, 진단 마지막 갱신은 40 ms, 현재는 160 ms다. 나이>100 ms를 stale로 분류하는 응용에서 무엇을 판정할 수 있는가? 로그와 진단의 한계 및 추가 증거를 설명하라.

## 해설

### Q1
이번 파일 항목은 최종 이름과 맞지 않는다. /r2/checker로 범위를 맞춘 뒤 선언·수락·실제 현재값과 적용 파일 버전을 확인한다. 시작 사건은 프로세스의 생성이고, 구성 성공·유효 관측·변환 준비는 별도 조건이다. 일정 시간 기다렸다는 사실만으로 이 조건들을 대체할 수 없다.

### Q2
구성 뒤 inactive, 활성화 뒤 active다. 구성 처리 20 ms, 대기 5 ms, 활성화 처리 8 ms다. 시작부터의 전체 시간은 프로세스 시작 시각이 주어져야 구한다. 사용자 작업은 상태 확인과 관리 대상 구현이 필요하므로 모든 구독의 자동 차단을 단정하지 않는다. 전이 이름만 쓰고 시간이나 한계를 생략하면 부분 답안이다.

### Q3
나이는 120 ms로 규칙상 stale다. INFO 누락은 WARN 필터와 일치하며 성공이나 실패의 부재를 입증하지 않는다. 진단 수준은 로그 심각도와 다른 체계이며 stale의 원인을 확정하지 않는다. 현재 설정·로그 대상·전이 결과·발행/진단 갱신의 동일 시계 기록이 필요하다. 콘솔이 조용하니 정상이라고 답하면 증거 범위를 넘는다.
