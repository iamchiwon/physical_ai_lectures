# P1 실행·실패 비교와 해설

아래 수치는 제공 config/frames와 runner의 실제 reference 실행에 대응한다. 파일명만 같은 다른 입력이나 설정을 쓰면 보고서의 SHA와 결과를 함께 비교한다. 일반 언어 문법 대신 영상/시간/명령 계약을 판정한다.

## 1. 두 책임과 정상 명령

감지는 RGB8 HWC 입력에서 빨강 마스크의 연결 성분과 중심을 만든다. 제어는 시각·단일 관측·복귀 조건을 확인한 뒤 가상 명령을 만든다. ROS 노드로 나눈다고 이 계약이 자동으로 지켜지지는 않는다. frame_id, captured_ms와 현재 시각의 영역·축·단위를 인터페이스에 보존해야 한다. 제공 실행은 로컬 파이프라인이며 ROS 메시지 전달을 실행한 기록은 아니다.

폭7의 기준은 x=3이다. x5의 정규화 오차는(5-3)/3=2/3, gain0.6 적용 후0.4, 제한 후0.25가상픽셀/스텝이다. x1은 -2/3→-0.4→-0.25다. 명령을 실제 바퀴 속도나 로봇 yaw 명령으로 그대로 바꾸지 않는다. 영상 x 증가 방향과 실물 명령 부호/단위는 별도 계약이다.

재생0행은 올바른 관측이어도 처음1회이므로 ACQUIRING·0명령이다. 1행에서 두 번째 유효 관측을 얻어 TRACKING·0.25다. “관측이 있으면 즉시 움직인다”는 해석은 복귀/초기 횟수 조건을 빠뜨렸다.

## 2. 상실·오래됨·잘못된 축과 복귀

- 2행: 마스크가 없어 LOST·0명령. 이전 양수 명령을 유지하지 않는다.
- 3행: 나이150-40=110ms가 TTL100을 넘으므로 STALE·0명령. 이미지에 빨강이 있어도 오래된 관측으로 재개하지 않는다.
- 경계 나이100ms는 아직 유효하다. 101ms부터 만료다. 이 경계는 테스트에서 별도로 확인했고 실제 센서 안전규격은 아니다.
- 4행: 정상 왼쪽 목표가 돌아왔어도 복귀 첫 관측이라 ACQUIRING·0명령. 5행에서 TRACKING·-0.25다.
- 6행: 분리된 빨강 성분2개로 AMBIGUOUS·0명령. 두 성분 평균을 실제 목표 위치로 오인하지 않는다. 4방향 이웃 기준이므로 대각선 접촉만으로 합치지 않는다.
- 7행: captured400>현재350으로 미래 시각이라 INVALID·0명령. TTL을 늘리는 것으로 고칠 시간 계약 문제가 아니다.
- 8행: width7인데 한 행의 픽셀 개수가6이라 INVALID·0명령. 원소 수만 맞추려고 축을 임의로 reshape하지 않는다.
- 9행: 다시 정상 관측이지만1회라 ACQUIRING·0명령. 10행은 TRACKING이며 중심x3이므로 오차0·명령0이다.

따라서 0명령은 LOST/STALE/AMBIGUOUS/INVALID뿐 아니라 관측 대기나 정상 목표 정렬에서도 나온다. 명령 수치만 저장하면 원인을 구별하지 못한다. 상태·이유·입력ID/시각을 함께 남겨야 한다.

역순/중복 frame_id·시각, 잘못된 RGB 범위·bool 픽셀·미래 관측도 소프트웨어 계약의 오류다. 읽을 수 없는 JSON/잘못된 설정은 전체 실행 실패와 stderr 이유로 보고한다. 이런 동작은 실제 로봇의 물리 정지를 실행한 증거가 아니다.

## 3. 재생과 명령 피드백의 차이

재생은 제공11프레임을 그대로 읽으므로 명령이 다음 영상을 바꾸지 않는다. 합성 폐루프는 각 명령 뒤 offset을 바꾸고 round(5-offset)로 다음 관측을 생성한다. 기본20스텝 reference에서 처음 관측오차2/3, 마지막0, 마지막 offset약1.7을 얻었다. 0/양수/음수의 부호와 경계는 SPEC를 따른다.

원인을 비교하려면 config를 별도 파일로 복사해 gain만0으로 바꾸고 새 보고서 파일명으로 같은20스텝을 실행한다. 명세의 허용 범위 안에서 한 조건을 바꾼 실험이며 기준 reference를 덮어쓰지 않는다. gain0에서는 명령0·offset0이 계속되어 오차가2/3에 남는다. 이 비교가 명령이 새 관측에 영향을 준다는 근거다. 단순히20개 결과 줄을 출력했다고 폐루프를 실행했다고 할 수 없다.

이는 작은 정적 장면·픽셀 양자화·무지연 모형이다. 실제 영상 잡음·목표ID·조명 변화·카메라 투영·관성·통신 지연·정지 안전을 검증하지 않았다. 물리 시뮬레이션이나 실제 Sim2Real 성과로 표시하지 않는다.

## 4. 제출물 판정

아래5항목이 모두 있어야 제공된 기본 경로 수행을 확인할 수 있다.

1. 같은 source/config/input 식별자와 Python/platform·실제 명령·실행 모드 기록.
2. 재생11행·상태 집계·오른쪽/왼쪽 포화 명령과0명령의 서로 다른 이유.
3. TTL경계·오래됨·잘못된 축/시각·다중 성분과2회 복귀의 근거.
4. 기본/이득0 폐루프 비교 및 고정 재생과의 차이.
5. 관찰→해석→미확인 범위를 나눈 보고. 실제 장비/ROS 성과를 덧붙이지 않음.

숫자 비교 허용오차1e-9는 계산 판정용이다. 플랫폼이나 Python 메타데이터를 무시해 환경이 완전히 같다고 주장하지 않는다. 테스트 성공 요약만 남기거나 입력을 고쳐 기준 출력과 맞춘 보고서는 부분 근거다. learner마다 실제로 수행한 범위만 제출한다.

저장소의 기존 Node test runner에 `tests/project-p1.test.mjs`를 추가해 스타터 자체의 동작을 검증한다. replay의 원본 불변/상실/복귀, 시계/축/픽셀 경계, CLI 출력 보호/실패, 기본 대비 gain0 피드백을 확인한다. 이 테스트는 모든 학생의 답안이나 실물 성능을 자동 채점하지 않는다.
