# P3 · 사례별 해설과 판정 근거

## 실행 결과를 읽는 순서

먼저 `source_sha256`, `config_sha256`, `input_sha256`와 실행 환경을 확인한다. 그다음 원사건 `events`, 실제 처리한 `decisions`, `processed_count`와 `unprocessed_count`를 대조한다. 마지막으로 로봇별 부분성과와 공동자원 상태를 읽는다. CLI 종료 코드 0은 보고서를 생성했다는 뜻이다. 물류 작업 전체의 성공이나 실제 출발을 뜻하지 않는다.

아래 실제 결과는 동봉 입력을 Python 3.12.11로 실행한 `reference/*.json`과 같다. 이 활동은 합성 사건 재생이다. 실제 ROS·fleet·로봇·물체·충돌 안전을 검증하지 않는다.

| 사례 | 사전 기대 | 실제 결과와 해석 |
|---|---|---|
| nominal | 두 로봇의 주행 결과·정지·작업/물체 확인·수납이 갖춰질 때만 출발 준비 확인 | 18사건 처리, DEPART_ALLOWED 2회, ready_robots=[r1,r2], READINESS_CONFIRMED. 예약과 점유는 비어 있다. 실제 출발·도착은 관측하지 않았다. |
| lease-expiry | 예약 만료만으로 실제 점유를 해제하지 않음 | 1000ms에 예약만 만료되고 r1 점유는 남아 WAIT_OCCUPIED. 1100ms r1 퇴장 관측 뒤 1200ms에 r2 예약만 GRANTED. 작업 준비는 미완료다. |
| cancel | 취소 수락을 정지·수납으로 해석하지 않음 | CANCEL_ACCEPTED_NOT_STOP_CONFIRMED 뒤 DENIED_CANCEL_PENDING. 팔 최종 종료와 수납을 생성하지 않았고 출발 준비는 미완료다. |
| no-stow | 작업과 물체 확인이 있어도 수납이 없으면 출발 차단 | task_verified=true를 보존하지만 arm_stowed=false, DENIED_NOT_STOWED다. 부분성과를 전체 완료로 바꾸지 않는다. |

| old-request | 과거 job의 진입을 현재 세대로 수용하지 않음 | 정상 예약 뒤 이전 job의 진입이 INVALID. 예약 이력은 보존하고 자원은 unknown으로 잠근다. |

## 1. 예약 만료와 점유 해제는 왜 다른가?

예약은 소프트웨어의 사용 허가다. 점유는 통로 안에 있는 로봇의 관측이다. 유효 구간은 `[허가 시각, 허가 시각+1000ms)`이므로 999ms에는 다른 로봇이 WAIT_RESERVED이고 정확히 1000ms에는 예약이 만료된다. **빈 통로라면** 새 예약을 허가할 수 있다. 그러나 lease-expiry 사례에서는 이미 r1이 진입했으므로 r2는 계속 WAIT_OCCUPIED다.

“예약이 끝났으니 통로도 비었다”는 답은 틀리다. 일치하는 r1 퇴장 관측이 추가로 필요하다. 예약 없는 진입이나 다른 로봇의 모순된 퇴장은 unknown을 만들며, 이후 예약을 막는다. 다른 로봇의 퇴장으로 기존 점유자를 지우지 않는다. unknown을 운영자가 해소하는 절차는 기본 모형의 범위 밖이다.

## 2. 주행 성공·작업 성공·취소 수락만으로 무엇을 알 수 있나?

같은 nav_goal_id의 SUCCEEDED는 주행 Action 결과다. 별도 `base_stopped.stationary=true` 관측이 없으면 팔 작업을 허가하지 않는다. 팔의 SUCCEEDED도 `object_verified=true`가 함께 있어야 작업 확인이다. 물체 확인이 없으면 수납 관측을 추가해도 DENIED_TASK_UNVERIFIED다.

작업 확인은 팔 수납 확인을 대신하지 않는다. 작업 요청 때 수납 상태를 false로 바꾸며, 이후 같은 arm_goal_id의 검증된 수납 관측이 필요하다. 취소 ack는 요청 수락일 뿐이므로 cancel 사례는 미해결 취소를 유지한다. “취소가 수락됐으니 팔이 멈추고 수납됐다”는 답은 정지·최종 종료·수납 증거를 생략한 것이다. 기본 모형에는 취소 후 자동 복구나 새 ID 자동 재시도가 없다.

## 3. 세 가지 시간 조건을 어떻게 구분하나?

- 사건 TTL은 100ms다. 같은 시계에서 `now−stamp=100ms`는 수용하고 101ms·미래 시각은 거부한다.
- 예약 lease는 1000ms이며 끝 시각을 포함하지 않는다. 만료는 허가만 없앤다.
- 저장된 정지·수납 관측의 state TTL은 1000ms다. 관측 나이 1000ms까지 유효하고 1001ms에는 새 관측이 필요하다.

정상 실행의 마지막 1700ms에서 r1 정지 관측 나이는 900ms, r2는 800ms다. 수납 관측 나이는 각각 300ms와 200ms다. r1의 정지 관측을 갱신하지 않고 출발 요청 시각만 1801ms로 늦추면 DENIED_BASE_STATE다. 정지를 새로 확인해도 수납 관측 나이가 1001ms이면 DENIED_NOT_STOWED다.

`departure_allowed_at_ms`는 과거 허가 시각이다. 이후 관측이 오래되거나 이동 상태가 들어오면 현재 `ready_to_depart=false`가 된다. 과거 허가를 현재 준비 상태로 복사하면 안 된다.

## 4. 잘못된 입력을 왜 멈춰야 하나?

clock·world/map·robot/namespace/frame·job/goal이 맞지 않거나 seq/now가 증가하지 않으면 현재 상태에 붙일 근거가 없다. INVALID_STOP으로 추가 처리를 멈추고 자원을 unknown으로 둔다. 원사건은 버리지 않고 처리한 접두열과 미처리 개수를 구분한다. 보고서 전체 `events`를 모두 실행한 것처럼 설명하면 틀리다.

잘못된 JSON·구성 누락·중복 로봇 식별자·잘못된 스키마는 CLI 종료 2로 거부한다. 입력·설정·소스와 기존 보고서는 덮어쓰지 않는다. 실험 조건을 바꾸려면 복사본과 새 출력 파일을 사용하고 지문을 남긴다. 식별자 검사는 인증된 센서나 권한 시스템을 구현한 것이 아니다.

## 학습자가 남길 네 가지 근거

1. **입력과 실행:** 실행 명령, 환경, 소스/설정/입력 지문, 실제 처리/미처리 사건 수를 적는다. reference를 자신의 실행 결과로 제출하지 않는다.
2. **예약과 점유:** lease-expiry의 1000·1100·1200ms 결정을 인용하고, 예약 만료와 퇴장 확인을 구분한다. 시간만 적고 점유 관측을 생략하면 부분 답안이다.
3. **실패와 준비:** cancel/no-stow 및 무효 입력 하나를 골라 마지막 판정·남은 부분성과·부족한 관측을 설명한다. Action 성공을 수납이나 물류 완료로 바꾸면 오답이다.
4. **확인 범위:** 두 로봇의 현재 준비 상태와 실제 출발/물체/안전 미확인 범위를 나눈다. state TTL을 바꾼 반례 하나와 추가로 필요한 실제 관측을 제시한다.

힌트: 결과 요약만 보지 말고 해당 시각의 `decisions[*].resource`와 `robots`를 비교한다. 첫 시도에서는 정상 사례, 다음에는 예약 만료, 그다음 취소/수납, 마지막으로 무효 입력 순서로 읽으면 전제와 실패 원인이 분리된다.
